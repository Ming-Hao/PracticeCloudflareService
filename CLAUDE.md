# CLAUDE.md

Guidance for Claude Code (claude.ai/code) when working in this repository.

## Project overview

URL shortener practice project on Cloudflare Pages: a Vue 3 SPA (`src/`) plus Pages Functions (`functions/`) backed by a D1 (SQLite) database. One frontend route; link history is stored client-side in IndexedDB, encrypted.

## Commands

```bash
npm install
npm run dev         # Vite dev server :5173, proxies /api/* to :8788
npm run build       # vue-tsc --build + production build to dist/
npm run type-check  # vue-tsc --build only
npm run preview
npm test            # node --test, runs __tests__/**/*.test.{ts,js} under src/ and functions/
npm run wrangler:types        # regenerate worker-configuration.d.ts from wrangler.toml
npm run wrangler:types:check  # fail if that file is out of date
```

No lint script is configured.

`worker-configuration.d.ts` is a generated file that is checked in, so type-checking needs no
generation step first. It supplies the Workers globals (`Env`, `EventContext`, `D1Database`,
`Response`) that `functions/` is checked against. Rerun `npm run wrangler:types` after changing a
binding in `wrangler.toml` — nothing does it automatically, and `npm run wrangler:types:check` is
the only thing that notices a stale file. That check compares the hash in the file's header
against what `wrangler.toml` would generate now; it reads none of the declarations below it, and
none of `functions/`. CI runs it on every pull request, ahead of the type check, so forgetting it
locally fails there rather than after deploying. It also covers the less obvious trigger:
upgrading `wrangler` changes the bundled workerd version and makes the file stale on its own.

Running the full stack locally needs **two processes at once**:

```bash
npx wrangler pages dev dist   # functions/ + D1 binding on :8788
npm run dev                   # SPA on :5173
```

The Vite proxy only forwards `/api/*` — `GET /:code` and `DELETE /:code` have to be exercised against `http://localhost:8788` directly.

First-time setup: apply `schema.sql` to the D1 database bound as `DB` in `wrangler.toml`:
`npx wrangler d1 execute shortlink-db --file=schema.sql`.

## Architecture

- **Frontend** — Vite + Vue 3 + vue-router, single route → `src/views/HomeView.vue`, which POSTs to `/api/shorten` and mounts the history UI (`src/components/history/`).
- **Backend** — Pages Functions, file-based routing: `functions/api/shorten.ts` (create), `functions/[code].ts` (`GET` → 302 redirect + click counter, `HEAD` → 200/404 stale-link probe that does not count, `DELETE` → soft-delete via `deleted_at`).
- **Database** — one `links` table (`schema.sql`), accessed through the `env.DB` binding. Always use `.prepare().bind()`; never string-interpolate SQL.
- **Client-side history** — `src/utils/crypto.ts` (PBKDF2 → AES-GCM; `decrypt` returns `null` on wrong password, doesn't throw), `src/utils/historyDb.ts` (IndexedDB, stores encrypted blobs only, `id` is a caller-generated UUID independent of `short_code`), `src/composables/useHistory.ts` (singleton reactive state, memory-only, resets on reload; `useHistory()` resolves through `inject(historyStoreKey, …)` so a test can provide its own store — see Gotchas).
- Pages build output dir is `dist` — the same output as the Vite build.

## Authorization model

The server never records who created a link. `delete_token` is returned **only** in the `POST /api/shorten` response and there is no other way to look it up, so the frontend must capture it immediately; possession of that token is the sole authorization check for delete.

Ownership therefore lives entirely client-side: encrypted under a user-chosen password (random salt/IV per record), never persisted, no recovery. The same link can be saved under more than one password, so one local copy can go stale after another deletes the server-side row — the frontend only discovers this reactively, on click (404) or re-delete (idempotent 200). See `removeStaleLocalOnly` / `onLinkClick` in `HistoryItem.vue`.

## Gotchas

Non-obvious constraints. Most of these fail silently when broken.

- **Both timestamp columns are written by hand** with `new Date().toISOString()` — `created_at` in `functions/api/shorten.ts`, `deleted_at` in `functions/[code].ts` — never by SQLite's `CURRENT_TIMESTAMP`, whose `YYYY-MM-DD HH:MM:SS` has no timezone marker and is parsed by browsers as *local* time. `created_at` reaches the frontend, so it is the one that breaks visibly; `deleted_at` is only ever tested for NULL today and matches purely for consistency. `schema.sql` still carries `DEFAULT CURRENT_TIMESTAMP` on `created_at` and live rows soft-deleted before this change keep the old format — neither is migrated, and nothing parses them.
- **`functions/[code].ts` response contract** is deliberate, not incidental. `GET` looks up `short_code` with `deleted_at IS NULL` — a query that drops that filter resurrects deleted links — and 404s when there's no match. `DELETE` 404s on an unknown code, 403s on a token mismatch, and treats re-deleting an already soft-deleted link with a matching token as an idempotent **200**, not an error; the frontend relies on that to detect stale local copies. A **non-string** `delete_token` is always a mismatch, and the `typeof` guard that enforces it is not redundant with the `!==` below it: `delete_token` was added by `ALTER TABLE`, so rows predating it hold NULL and the column has no `NOT NULL` constraint, which made `{"delete_token": null}` compare equal and delete those links unauthorized. Keep the guard on the same `if` as the comparison rather than hoisting it above the `if (!link)` check — moving it turns an unknown code with a non-string token into a 403 and breaks the 404 contract above.
- **The 302** in `functions/[code].ts` is hand-built rather than `Response.redirect()`, which returns immutable headers that can't take `Cache-Control: no-store`. Without `no-store`, a cached redirect outlives edits/deletes and stops the counter.
- **Click counting** is handed to `context.waitUntil`, not awaited. Tests hitting that route must `await ctx._settle()` before the test DB is disposed, or the background write fails with `ERR_DISPOSED`.
- **`functions/[code].ts` has two read entrypoints**: `onRequestGet` (counts a click) and `onRequestHead` (does not — it's the frontend's stale-link probe before navigating, `src/utils/linkClick.ts`). They run the same `short_code` + `deleted_at IS NULL` lookup independently; changing one's query without the other reopens the double-count bug this split was fixing, or makes HEAD and GET disagree on whether a link exists. `onRequestHead` answering **200** rather than mirroring GET's 302 is equally deliberate, and `resolveLinkClick` depends on it: the probe uses fetch's default `redirect: 'follow'`, so a 302 here would be followed cross-origin to the target site, fail CORS, and reject. RFC 9110 says HEAD should mirror GET, which makes this a plausible thing for someone to "correct". Only half of it is guarded: `code.test.ts` asserts HEAD answers 200 with no `Location`, so the server side goes red. The client side does not — `linkClick.test.ts`'s fake fetch returns a hand-built `Response`, which never follows a redirect the way the real one does, so nothing there notices. Changing HEAD to 302 means adding `redirect: 'manual'` back to `resolveLinkClick` in the same change.
- **Error responses that a script reads** are always `Response.json({ error })`, never plain text, so the frontend can always `await res.json()`. That covers `POST /api/shorten` and `DELETE /:code`. The one exception is `GET /:code`'s 404: a visitor arrives there by navigation, so it returns an HTML page (`notFoundPage()`) with `Cache-Control: no-store` — nothing calls that route expecting JSON, the HEAD probe reads only the status. Don't "fix" it back to JSON for consistency.
- **URL validation** (`functions/api/shorten.ts`): reject non-strings and inputs over `MAX_URL_LENGTH` (2048) first, then reject `\0`, `\n` and `\r`, then `new URL()` in try/catch, then check `protocol` is `http:`/`https:`, then refuse the request's own hostname, then refuse a private/loopback/link-local target (`isPrivateHostname`). Never use prefix checks like `url.startsWith('http')` — that was tried first and let mismatched protocols and embedded whitespace through. (The self-hostname check only sees the hostname the request arrived on; a deployment reachable under both `*.pages.dev` and a custom domain can still shorten a link to its other hostname. Accepted for this project.)
- **`target_url` stores the raw request string, not `parsedUrl.href`**, so every check above validates one string while the database keeps another. They differ in case, leading/trailing spaces and tabs; none of that reaches the browser wrong, because a header value is trimmed on both ends and tab is legal inside one. `\0`, `\n` and `\r` are the exception, which is why they are rejected on the raw input *before* `new URL()` — the parser removes LF and CR outright and accepts NUL, so afterwards there is nothing left to detect, and the row that gets written makes `GET /:code` throw while building its 302, on every request, for as long as it exists. Only its `delete_token` can retire it, and that was returned once. Normalizing on write (`parsedUrl.href`) would close the gap in one line but rewrites what the user typed — deliberately not done.
- **`isPrivateHostname`** (`functions/api/shorten.ts`) checks only the hostname as `new URL()` already normalized it — it relies on that normalization having folded octal/hex/integer/IPv4-mapped forms into a plain dotted-quad or bracketed IPv6 literal, and does not redo any of that parsing itself. It has no way to see a domain name that only resolves to a private address at request time (DNS-level bypass); that's out of scope by design, not an oversight.
- **A file under `functions/` becomes a route by exporting `onRequest*`**, not by where it sits. Wrangler scans every `.ts`/`.js` under `functions/` and matches export names against `onRequest(Get|Post|Put|Patch|Delete|Options|Head)?`; `__tests__/` is not special-cased, it simply exports none. That scan runs with `bundle: false`, so the `miniflare` and `node:fs` imports in the tests are never resolved and never reach the deployment — but a test file that exported an `onRequest*` name would publish a route. The scan does parse every file, so a `.ts` file it cannot parse fails the build.
- **`params.code` is typed `string | string[]`** (`Params<P>` covers catch-all routes too), and the handlers in `functions/[code].ts` narrow it with `as string`. That assertion is only sound because `[code]` is a single dynamic segment. A catch-all route would make the array case real, and the assertion would then hide it.
- **`functions/` deliberately does not enable `noUncheckedIndexedAccess`**, unlike `tsconfig.app.json` and `tsconfig.test.json`. `shorten.ts` indexes into `CODE_ALPHABET` and into arrays whose length a regex or an early return has already established, so the flag buys nothing there and costs a run of `!` assertions on code that is already guarded.
- **In `functions/__tests__/`, Workers objects must not be passed straight into `node:` APIs.** Both `worker-configuration.d.ts` and `@types/node` are in scope there, and `URL` is declared by both — the Workers one wins, and it is not assignable to node:fs's `PathLike` (their `searchParams.entries()` iterators differ). `helpers.ts` reads `schema.sql` through `fileURLToPath(new URL(...).href)` for exactly this reason: only a string crosses the boundary. Anything else shared between the two global sets will fail the same way.
- **miniflare's `D1Database` type does not resolve in this project**: its d.ts imports the type from `@cloudflare/workers-types`, which is not installed (wrangler now supersedes it with `wrangler types`). `skipLibCheck` hides the failure and the type collapses to `any`. `createTestDb` in `functions/__tests__/helpers.ts` pins the result to the generated global instead; dropping that assertion silently switches off type-checking for every `db.prepare(...)` in the function tests.
- **`PBKDF2_ITERATIONS` (`src/utils/crypto.ts`) can be raised at will; already-stored history is unaffected.** Each identity records the count it was created with in IndexedDB, and unlocking derives from *that* number, not from the constant — so after the 100k → 600k raise, identities created earlier still open with their original 100k while new ones use 600k. Differing counts across identities in one browser are expected; there is no migration and none is needed. The constraint this buys is one-directional: any change that derives an existing identity's key from the constant instead of `identity.iterations` makes that history undecryptable, and `decrypt` returning `null` is indistinguishable from a wrong password, so it surfaces as "wrong password" with nothing logged. Tests won't catch it either — every fixture builds its identity from the current constant.
- **`#app` is a `min-height: 100vh` flex column** (`src/assets/main.css`) purely so the footer reaches the bottom of the viewport; this page is short, so without it `AppFooter.vue` lands mid-screen right under the form. It has exactly two children: `.page-content` (`flex: 1 0 auto`, which does the pushing) and the footer. Everything else stays wrapped inside `.page-content` — promoting a block laid out with `margin: 0 auto` (`.how-it-works`, `.shortener`) to a direct child makes it a flex item, and a cross-axis auto margin cancels `align-items: stretch`, so it silently shrinks to its content width and its `max-width` stops mattering.
- **`__APP_COMMIT__`** (`vite.config.ts`) is `CF_PAGES_COMMIT_SHA` on Cloudflare Pages and `git rev-parse` locally; it is `''` when neither is available (e.g. a build from a tarball with no `.git`). `AppFooter.vue` drops the whole segment on empty rather than rendering a broken commit link — keep the `v-if`.
- **The footer's commit hash is revealed by hovering `.repo-group`, not the GitHub link itself.** It is `pointer-events: none` while invisible, so a rule keyed on `.repo:hover + .hash` un-hovers the moment the pointer leaves the link and the hash can never be clicked — the wrapper keeps the whole travel path inside one hover target. Everything that hides it lives inside `@media (hover: hover)`, so a touch device shows it by default and needs no rule of its own — an `@media (hover: none)` block restating `opacity: 1` is dead weight, and there used to be one.
- **Native `<dialog>`** can't rely on the browser's default modal centering — the global `* { margin: 0 }` reset in `src/assets/base.css` overrides it. Center explicitly: `position: fixed; top/left: 50%; transform: translate(-50%, -50%); margin: 0`.
- **`public/_routes.json`** is hand-written and overrides Wrangler's generated version, which would be `{"include":["/*"],"exclude":[]}` because `functions/[code].ts` is a root-level catch-all — waking a Function once per static asset. Any new path that must reach a Function has to stay out of `exclude`; getting it wrong fails silently, so exercise the route after adding one. The reverse also holds: any static asset path has to stay *in* `exclude`, or it's treated as a `short_code` lookup and 404s instead of serving the file — this is why both `/` and `/index.html` are listed even though they resolve to the same file.
- **`public/_headers`** CSP deliberately omits `'unsafe-inline'`. That only holds because nothing emits inline script/style — no `:style` bindings, no `v-show`, no `<Transition>`, no external fonts or CDNs. Introducing any of those must widen the CSP in the same change. `_headers` applies to static responses only; Function responses set headers in code — which is why `notFoundPage()` in `functions/[code].ts` can carry an inline `<style>` without contradicting this. That page sets `X-Content-Type-Options` and `X-Frame-Options` in code, since nothing else can set them for it, but deliberately no CSP — it loads nothing external and runs no script, so restating one there would be ceremony.
- **Tests** run on Node's built-in runner with type-stripping (no ts-node/vitest). Non-erasable TS syntax — e.g. `constructor(public x: number)` — breaks; keep test-covered classes plain-JS-shaped. The same limit applies to `functions/`, which Node type-strips too — both function tsconfigs set `erasableSyntaxOnly` so the compiler reports it rather than the test run. There is no component runner either, so `.vue` files are untested — but Vue code that only needs an app context still is, without adding one: `createApp({})` works in a DOM-less Node process and `app.runWithContext()` makes `inject` resolvable. That is how `useHistoryInjection.test.ts` runs.
- **Every connection to the history DB has to be closed**, in `src/utils/historyDb.ts` and in tests alike. `openDb()` registers no `onblocked`, so a connection left open anywhere blocks the next `DB_VERSION` upgrade and the open request never settles — the caller waits forever with nothing logged. New exported functions go through `withDb`; new test helpers `close()` before resolving. `historyDb.connections.test.ts` guards this, and pins the per-operation open/close design: a cached long-lived connection would fail it even if it handled `versionchange` correctly.
- **A blocked upgrade cannot be tested by provoking one.** An IndexedDB open request has no abort, and fake-indexeddb re-queues a blocked one through `setImmediate` until the blocker closes, so the `node --test` process never exits — the run hangs instead of reporting. Count open connections instead (see `historyDb.connections.test.ts`).
- **IndexedDB tests** run against `fake-indexeddb`. Call `resetIndexedDb()` (`src/utils/__tests__/indexedDbHelpers.ts`) from `beforeEach`, not per test — it's global state a new test can silently forget.
- **`HistoryDbDeps` has two implementations** — the real one and the in-memory fake in `src/utils/__tests__/fakeHistoryDb.ts` (`createFakeDb`), shared by `useHistory.test.ts`, `useHistoryInjection.test.ts`, and `historyDb.contract.test.ts`. Reuse it instead of hand-rolling a third: only the two are under contract. `historyDb.contract.test.ts` runs one assertion set against both and is the only thing that detects drift; a stale fake leaves every `useHistory` test green while describing a storage layer that no longer exists (already happened once). Fix whichever implementation is wrong — never relax the contract.
- **`useHistory()`'s `?? store` is load-bearing**, despite a type signature saying `inject` with a default can never return `undefined`. It can: Vue skips the default entirely and returns `undefined` when there is neither a component nor an app context, so deleting the `??` turns every call outside `setup()` into a `TypeError` on destructuring. Relatedly, a component only receives a *provided* store when `useHistory()` is called at `<script setup>` top level — calling it from an event handler silently falls back to the singleton, which in a test means the assertions run against the wrong store. All four call sites are currently top-level; keep it that way. `useHistoryInjection.test.ts` pins both behaviours without needing a component runner, via `app.runWithContext()`.

## Conventions

- Everything is TypeScript, but `functions/` and `src/` are checked as separate projects with different globals: `tsconfig.functions.json` / `tsconfig.functions-test.json` give `functions/` the Workers globals from `worker-configuration.d.ts` and no DOM lib, while `tsconfig.app.json` / `tsconfig.test.json` give `src/` the DOM. Backend code must never be moved under a `src/` project or vice versa — `Response` and `Request` mean different things on each side.
- Pages Functions handlers annotate the context parameter (`context: EventContext<Env, 'code', unknown>`) instead of using `PagesFunction`. `PagesFunction` is a function type, so it can only be applied to a `const`, and adopting it would mean rewriting every `export async function onRequest*` as an arrow function. `onRequestPost` in `shorten.ts` could not use it at all — it takes a second parameter as a test seam.
- All code, comments, and user-facing strings in English — do not introduce Traditional Chinese.
- The two marks in `AppFooter.vue` are the **only** icons exempt from the outline convention below: they are the official GitHub and Cloudflare logos (solid, single-path, `fill` rather than `stroke`), so redrawing them as 2px outlines would make them wrong rather than consistent. The Cloudflare cloud also keeps its brand `#f6821f` instead of `currentColor`.
- Reuse `.btn-primary` / `.btn-secondary` / `.btn-icon` from `src/assets/buttons.css` (imported globally via `main.css`) instead of redefining button styles in `<style scoped>`. Icons follow the shape used in `HomeView.vue`: 24×24 viewBox, `stroke="currentColor"`, `stroke-width="2"`, `class="btn-icon"`.
- Before adding a dialog under `src/components/history/`, check whether an existing one can be parameterized. `ConfirmDialog.vue` already doubles as the binary "use current identity vs. save with a new password" prompt, deliberately avoiding a sixth component.
- Destructive/dismissive actions add `.btn-danger` on top of `.btn-secondary`, switching the green hover to a red wash. Reuse it rather than inventing a new red variant.
- Bumping `version` in `package.json` also means adding a matching `## [x.y.z]` entry (with compare link) to `CHANGELOG.md` and creating a `vX.Y.Z` git tag on that commit. The version the UI shows comes from `__APP_VERSION__`, injected by `define` in `vite.config.ts` — never hard-code it in a component.
- **Secondary text uses `--color-text-muted`, never `opacity` on `--color-text`.** `--color-text` is already `rgba(..., 0.64)`, so the two alphas multiply: the `opacity: 0.7` this replaced landed at 3.7:1, under the 4.5:1 WCAG 1.4.3 wants. Nothing in this UI reaches the 24px (or 18.66px bold) that would earn the 3:1 exception, so every colour choice here is measured against 4.5:1, and `#fff` on the accent green is not one of them — both count badges failed at 2.10:1 and 4.14:1. `opacity` is still correct where it drives a transition rather than a shade, as with the footer's hash reveal.
- **The background to measure a colour against is `--color-background-mute`, not the panel it looks like it is on.** `.history-section` (`HistoryDrawer.vue`) paints mute over the soft drawer, so `.history-item-target`, `.history-empty` and `.history-item-error` sit one shade lighter than the drawer itself — the worst case in the app, and the one that binds `--color-text-muted` and `--color-danger`. Both shipped at values chosen against soft and quietly missed on mute (4.47:1 and 4.23:1) until they were re-measured. The same class name proves it: the drawer's own `clearError` / `loadError` render *outside* `.history-section`, on soft, where the identical colour already passed.
- **Colors live in `base.css`; `<style scoped>` blocks reference them.** The accent and danger colors each come in two forms, and the pair is the reason the variables exist rather than literals: `--color-accent` is a foreground (text, borders, the drawer's section marker), `--color-accent-surface` is a background dark enough to hold a white label. They differ by about one shade and are not interchangeable — using the foreground form as a surface drops its white text to 4.14:1, which is exactly the bug this pair was extracted to prevent. `--color-danger` / `--color-danger-surface` split the same way. What stays literal is what belongs to one element and one place: `App.vue`'s `#e67e22` heading, `AppFooter.vue`'s Cloudflare `#f6821f`, `HomeView.vue`'s `#3a3a3a` input, the saved-section `#3498db`.
- **This project is dark-only.** `base.css` declares `color-scheme: dark` and has no `prefers-color-scheme` branch, deliberately; `index.html` carries a matching `<meta name="color-scheme">` so the first paint is dark too. There is no palette tier above the semantic variables either — the Vue starter's `--vt-c-*` set existed to be chosen between, and with one theme it only renamed values. Reintroducing a light branch is a whole-project change, not a two-line addition: every value in `base.css` needs a second form, and the literals listed above need auditing (`#2ecc71` sits at 2.08:1 on white, and `#3a3a3a` behind `--color-text` is what made the typed URL invisible before). `notFoundPage()` in `functions/[code].ts` holds its own copy of these colors and has to change in the same commit — nothing imports across that boundary, and no test compares them.

## Workflow

- For UI with no visual precedent in the repo (a brand-new drawer, dialog, or page layout), produce a local HTML mockup via the mockup skill and get it approved before editing `src/`. Layout/spacing/color tweaks to existing components don't need this.
- When one change touches styles across two or more `.vue` files, run `/simplify` before wrapping up to consolidate duplicated styles into shared files like `src/assets/buttons.css`.
